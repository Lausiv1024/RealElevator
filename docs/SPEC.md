# Real Elevator 仕様書

2026-10-13 時点

## 概要とコンセプト

日本式エレベーターの操作感と挙動を、マイクラのドット絵の世界観で再現するNeoForge用MODを作る。

- **操作**：実機の日本式エレベーターと同じ操作方法（乗場ボタン、かご操作盤、開・閉ボタン、2度押しキャンセルなど）
- **見た目**：マイクラのドット調を維持しつつ、日本のエレベーターのデザインに即したもの（マイクラ × リアルの融合）
- **寸法**：実機資料の1.5倍スケール（プレイヤーの体格に合わせるため）
- **方針**：基本はリアル志向。ただし動力や設置まわりはマイクラらしいパワープレイを許容する

## 開発環境と構成

NeoForge・Minecraft 1.21.1で開発し、Minecraftに依存しないロジックを`core`モジュールとして分離する。

MOD名は**Real Elevator**、mod idは`realelevator`とする。

| 項目 | 決定内容 |
| --- | --- |
| ローダー | NeoForge |
| 対象バージョン | 1.21.1（以降のバージョンにも順次展開） |
| 言語 | Java |
| ビルド | Gradleマルチモジュール |

**モジュール構成**

- `core`（純粋なJava、MC非依存、JUnitでテストする）
  - 運転曲線（S字加減速、時刻から位置を求める関数）
  - 運行制御（呼びの登録、2度押しキャンセル、乗合全自動、将来の群管理）
  - ドアの状態遷移（反転、ナッジング、開放待機時間）
  - アナウンスのテンプレートと音声Providerのインターフェース、VOICEVOXクライアント
- `neoforge-1.21.1`（MC依存の薄い層）
  - エンティティ、ブロック、描画、Mixin、ネットワーク、サウンド再生
  - `core`のクラスはMODのjarに同梱し、開発時の起動でも同じMODとして読み込む。
- MOD共通の値（mod id、バージョンなど）はルートの`gradle.properties`、Minecraft・NeoForge・Parchmentのバージョンは各バージョンのモジュールの`gradle.properties`に置く。
- パッケージは`net.lausiv1024.realelevator`。`core`は`net.lausiv1024.realelevator.core`以下に置く。

**多バージョン展開**

- 対応バージョンが増えた段階で、Stonecutter（プリプロセッサ方式）の導入を検討する。
- 1.21.2前後でエンティティの描画がRenderStateベースに変わる見込みのため、レンダラーは書き直しを前提とする。
- Mixinは最小限にし、1クラスに集約する。

## 寸法

JIS A 4301の乗用エレベーターを基準に1.5倍し、ドット格子を揃えるため1/16ブロック（1px）単位に丸める。

| 項目 | 実機 (mm) | ×1.5 (ブロック) | 丸め後 (ブロック / px) |
| --- | --- | --- | --- |
| P-9 かご内 幅×奥行 | 1400×850 | 2.1×1.275 | 2.125×1.25 / 34×20 |
| P-11 かご内 幅×奥行 | 1400×1100 | 2.1×1.65 | 2.125×1.625 / 34×26 |
| P-13 かご内 幅×奥行 | 1600×1350 | 2.4×2.025 | 2.375×2.0 / 38×32 |
| 出入口幅（P-9・P-11） | 800 | 1.2 | 1.25 / 20（※） |
| 出入口幅（P-13） | 900 | 1.35 | 1.375 / 22 |
| 出入口高さ | 2100 | 3.15 | 3.125 / 50 |
| 天井高 | 2300 | 3.45 | 3.4375 / 55 |
| トランサム高さ | 200 | 0.3 | 0.3125 / 5 |

- 1ブロック＝1mとして換算する。実機の値は概算のため、実装前にJISの資料で確認する。
- ※ P-9・P-11の出入口幅は、丸めると19pxになるが、中央開きの戸を同じ幅の2枚（10pxずつ）に分けられるよう20pxにする（実機換算 約833mm）。左右の袖壁は7pxずつになる。
- かごは端数を含む寸法になるため、ブロックの組み合わせではなく独自モデルと独自当たり判定を持つエンティティとして実装する。
- ピット深さと頂部すき間は「リアル寸法／省スペース」を選択できるようにする。
- かごの厚みは、壁1px・床2px・天井2pxとする（実機の概算を1.5倍して丸めた値）。表の寸法は内法で、外形はこの分だけ大きくなる。
- 出入口は正面の袖壁の中央に置く。左右の袖壁の幅が1px違う場合（P-9・P-11は7pxと8px）は、片側を広くする。

## 移動方式と運転曲線

かごはエンティティとして実際に昇降させ、プレイヤーが普通のブロックの上に立っているのと同じ感覚で運ぶ。

**速度仕様**（実機の速度×1.5）

| 仕様 | 実機 (m/min) | MOD (m/s) | 1tickあたり (ブロック) |
| --- | --- | --- | --- |
| 普通（低） | 60 | 1.5 | 0.075 |
| 普通（高） | 105 | 2.6（2.625を丸める） | 0.13 |
| 高速 | 300 | 7.5 | 0.375 |
| 超高速 | 600 | 15 | 0.75 |

- 加速度も1.5倍とし、約1.5 m/s²を基準にする。
- ジャークも実機値（約1.0 m/s³）の1.5倍とし、1.5 m/s³を基準にする。実機のジャークは0.7〜1.4 m/s³程度。高速仕様（高速・超高速）は標準で2.0 m/s³とする（試行値）。
- 加減速はジャーク制限付きのS字曲線にする。
- 高速仕様は、加速度とジャークを設定で上げられるようにする。短い行程では最高速度に届かないため（例：Y64→−59の約123ブロックでは超高速でも片道約18秒。ジャーク2.0を含めると約19秒）。
- 到着時には、床面を階のY座標にぴったり合わせる「着床」処理を行う。

**運転曲線の実装**（`core`の`TravelCurve`／`TravelLimits`）

- 単位はブロックと秒。上限値は最高速度・最大加速度・最大ジャークの3つ（`TravelLimits`）。
- 速度の仕様は`SpeedSpec`（普通（低）／普通（高）／高速／超高速）で、標準の加速度とジャークを持つ。
- 停止から停止までの7区間のS字曲線（ジャーク＋／加速度一定／ジャーク−／定速／ジャーク−／加速度一定／ジャーク＋）。減速側は加速側の鏡像として計算する。
- 行程が短い場合は、最高速度に届かない曲線（定速なし）、さらに短い場合は最大加速度にも届かない曲線に自動で切り替える。
- 時刻から位置・速度・加速度を閉じた式で求める。tick数（partialTick込み）からも求められる（20tick＝1秒）。
- 到着時刻以降は行先の位置をそのまま返し、これを着床とする。

**同期と運搬**

- **決定論的な運転曲線**：サーバーは発車情報（開始tick、出発階、行先階、曲線のパラメータ）だけを送る。クライアントは同じ曲線から位置を計算し、partialTickで描画する。バニラのエンティティ補間による遅延を避けるため。
- **プレイヤーの運搬**：ローカルプレイヤーの移動処理の直前に、かごの移動量をクライアント側で加算する。
- **サーバー側の検証**：サーバーでも同じ曲線でかごの移動量を加味し、「moved wrongly」による巻き戻しを防ぐ。
- **当たり判定**：床・壁・天井・扉の形状を独自のVoxelShapeとして定義し、Mixinでエンティティ衝突の収集処理に差し込む。onGroundが正しく立つので、落下ダメージの問題は起きない。
- **飛行キック**：バニラの浮遊判定は足元のブロックしか見ないため、かごの下が空間だとキックされる。かごの中にいるプレイヤーは、浮遊時間をサーバー側でリセットする（アクセストランスフォーマーを使う）。
- 昇降は同じチャンク列の中で完結するため、高速でもチャンク読み込みの問題は起きにくい。

**実装メモ**

- かごの位置、当たり判定、運搬量は、すべてゲーム時刻から運転曲線で求める。かごと乗っているエンティティのどちらが先にtickしても、同じ位置になる。
- 運搬するのは、クライアントではローカルプレイヤー、サーバーではプレイヤー以外のエンティティ。かごの外形の真上か中にいるものを運ぶ。
- 運搬量は「1tick分の移動量」ではなく、前のtickからかごが実際に動いた量とする。クライアントのゲーム時刻はサーバーの時刻に合わせて数tick飛んだり戻ったりするので、1tick分の量だと高速走行で床の中に取り残され、下へ抜け落ちる。
- 念のため、走行中のかごの床や屋根に足が入り込んだエンティティ（深さ1ブロックまで）は、その上面へ押し上げる。
- 到着したtickの移動量も運べるよう、サーバーは走行情報を到着の1tick後に消す。
- 発車情報はエンティティの同期データで送る。保存時に走行中だった場合は、ゲーム時刻に合わせて続きから走る。

## 昇降路の機構と描画

防犯窓や展望ガラス越しに見えるよう、巻上機・シーブ・ロープ・釣合い重りをかごの動きと連動させて描画する（必須要件）。

かごと釣合い重りはロープで直接引かず、シーブをかませて動滑車のように吊る。

**構成（機械室レス、2:1ローピング）**

```
  ロープ端(固定)                        ロープ端(固定)
  ═╤══════════════════════════════════════╤═  ← 昇降路頂部
   │                    (巻上機)          │
   │                   ╭─────╮            │
   │                   │  ●  │            │
   │                   │     │            │
   │   ┌───────────┐   │     ╰──(シーブ)──╯
   │   │           │   │        ┌──┐
   │   │    かご    │   │        │CW│  ← 釣合い重り
   │   │           │   │        └──┘
   │   └───────────┘   │
   ╰─(シーブ)────(シーブ)─╯   ← かご下シーブ
```

- 巻上機：昇降路の頂部に設置する。
- かご側：かごの下部にシーブを付け、ロープをかごの下にくぐらせる。
- 釣合い重り側：釣合い重りの上部にシーブを付ける。
- ロープの両端は昇降路の頂部に固定する。
- 昇降路の寸法には、釣合い重りとそのレールの分も含める。

**運動の関係**

- 釣合い重りは、かごと逆向きに同じ速さで動く。
- 2:1ローピングのため、巻上機の綱車の周速はかごの速度の2倍になる。
- 各シーブは、ロープの動きと半径から回転角を求めて回す。

**描画**

- かごと同じ運転曲線から、釣合い重りの位置、各シーブの回転角、ロープの長さを計算する。そのため追加の同期は不要。
- ロープは、固定点とシーブの接点を結ぶ区間ごとの線として描く。
- 見えていないときは、距離やカリングで描画を省略する。
- 細部はCodeで作業しながら決める。

## 運行制御と操作方法

操作方法は日本式エレベーターに合わせ、制御方式は乗合全自動を基本とする。

**乗場**

- ▲▼ボタン
- 階床表示器
- ホールランタンと到着チャイム

**かご内**

- かご操作盤は正面（ドアがある面）の袖壁に、ドアの横に並べて配置するのを基本とする。行先ボタンは2列配置
- ▶◀（閉）／◀▶（開）ボタン
- インターホン
- 2度押しで行先をキャンセルする機能
- 車椅子用操作盤（低い位置に設置し、押すと戸開時間を延長する）

**制御**

- 乗合全自動：呼びを進行方向順に処理する。
- 複数台の群管理は後のフェーズで実装する。
- ボタンは操作盤上のボタン単位で当たり判定を持たせ、レイキャストで押下を判定する。

**ボタンと運行制御の実装**（`core`の`CollectiveControl`／`ButtonLayout`）

- ボタンは2px角で、取り付け面から1px出っ張る。右クリックで押し、視線の先をボタン1つずつの箱でレイキャストする。ブロックより手前にあるときだけ押せ、届く距離はブロックと同じ。
- かごの操作盤は、かごの中から扉の方を向いて右側の袖壁に置く。設定で両側の袖壁に置くこともできる（左右とも同じ並びで、どちらのボタンでも同じ呼びになる）。行先ボタンは2列で、下の段から順に左の列に奇数階、右の列に偶数階を並べ、その下の段に開・閉ボタンを置く。
- 乗場の▲▼ボタンは、フェーズ1では乗場の扉のエンティティが持ち、乗場から見て出入口の右側（戸が滑り込む範囲の外側）に置く。最上階は▼だけ、最下階は▲だけ。
- 登録された呼びのボタンは応答灯がつき、応えると消える。
- 乗合全自動は、進行方向にある呼びを近い順に処理する。上昇中はかご呼びと上りの乗場呼びの階に止まり、その先に止まる階がなければ最も上の下りの乗場呼びまで行って反転する（下降中も同様）。
- 停止中で方向が決まっていないときに呼びが登録されたら、戸が開いていてもその場で呼びの方へ方向を決める（方向灯をすぐにつける）。
- かごが止まっている階の呼びは、登録せずにその場で戸を開く。ただし進行方向と逆の乗場呼びは、進行方向の先に呼びが残っていれば登録して後で応える。
- 乗場呼びに応えたときは開放待機を乗場呼びの長さに、かご呼びだけなら短い方にする。
- 走行中に、行先より手前の階にかご呼びか進行方向の乗場呼びが登録されたら、減速が間に合う限りその階に止まる。間に合わなければ通過し、呼びは残して後で応える。
  - 判定：運転曲線は加速をできるだけ長く続けてから減速する形なので、出発時点から途中階まで改めて計画した曲線が、今の位置・速度・加速度と一致していれば減速が間に合う。
  - 止まる場合は、発車情報の行先だけを差し替える（出発時刻と出発位置は同じ）。位置は途切れずにつながり、送るものも発車情報のままでよい。

**階床表示の実装**（`core`の`FloorIndicator`／`DotFont`）

- 表示は階名（2文字まで）と進行方向の矢印。1ドット＝1pxのドットマトリクスで、文字は3×5ドット、矢印は5×5ドット。点灯色はアンバー（光り方の選択はフェーズ4のデザインシステムで行う）。
- 並べ方は、横長（矢印、階名の順。14×5px）と縦長（上に矢印、下に階名。7×11px）の2通り。
- 表示器の位置は選べる。初期値は、乗場は扉の上、かごは右側の操作盤の上。
  - 乗場・扉の上：出入口の上の中央に横長で、ふち1px（16×7px）。
  - 乗場・ボタンの上：乗場のボタンの上に縦長。
  - かご・扉の上：出入口の上のトランサム（高さ5px）に、横長でふちなしで埋め込む。
  - かご・操作盤の上：操作盤の袖壁の行先ボタンより上に縦長。操作盤が両側のときは、左側にも付けるかを選べる。
- 三方枠・幕板ができるまでは、乗場の表示器は乗場の扉のエンティティが持つ。
- 表示器と操作盤の配置の設定は、今はデバッグ用コマンドで変え、ウィザードができたら制御盤のGUIで選べるようにする。
- 表示する階は、かごの位置に最も近い停止階（階と階の中間を過ぎると切り替わる）。かごの位置から各クライアントで求めるので、追加の同期はいらない。
- 矢印は、走行中はその向き、停止中は次に進む方向が決まっているときだけ出す。
- 階名は、階名を設定する仕組み（ウィザード）ができるまで、下から1、2、3…とする。文字は数字と、B・F・G・L・M・P・R・-に対応する。

## ドア

ドアは状態遷移で制御し、セーフティシューと多光軸ビームセンサーの両方で反転させる。

**状態遷移**

| 現在の状態 | 条件 | 次の状態 |
| --- | --- | --- |
| 閉 | 呼び | 開動作 |
| 開動作 | 全開 | 開放待機 |
| 開放待機 | 待機時間終了／「閉」ボタン | 閉動作 |
| 開放待機 | 開放が30〜60秒程度続く | ナッジング |
| 閉動作 | セーフティシュー／ビームで検知 | 開動作（反転） |
| 閉動作 | 反転が何度も続く | ナッジング |
| 閉動作 | 全閉 | 閉 |
| ナッジング | 全閉 | 閉 |

**検知**

- **セーフティシュー（接触式）**：閉まりかけの戸先にエンティティのAABBが触れたら反転する。
- **多光軸ビームセンサー（非接触式）**：かごの扉と乗場の扉の間に、出入口の全高（約3.125ブロック）にわたる薄い検知領域を置く。閉動作中にエンティティが入ったら反転する。

**開放待機時間**

- 乗場呼びのときは長め、かご呼びのときは短めにする。
- 車椅子用操作盤から呼んだ場合は延長する。
- 「閉」ボタンで短縮できる。

**ナッジング（強制戸閉）**

反転が何度も続いた場合、または扉が一定時間（30〜60秒程度）開いたままになっている場合は、ブザーを鳴らしながら低速で強制的に閉める。

**その他**

- 扉の方式：中央開き（CO）／2枚片開き（2S）。二方向出入口（かごの前後に扉）にも対応する。
- かごの扉と乗場の扉は連動して動かす。
- 同期はかごと同じく「開始tick＋状態」だけを送り、扉の位置はクライアント側で計算する。

**扉の実装**（`core`の`DoorController`／`DoorGeometry`）

- 開閉時間と開放待機時間は実機並みとする（寸法と速度がどちらも1.5倍なので、時間は実機と同じ）。開くのに2.0秒、閉じるのに2.5秒。開放待機は乗場呼びで4秒、かご呼びで2秒。
- 開き具合は0（全閉）〜1（全開）で表し、動き始めと止まる直前をゆっくりにする。反転したときは、その時点の開き具合から残りの分だけの時間で開き直す。
- 戸の厚みは1px。かごの戸は袖壁のすぐ外側、乗場の戸はさらに敷居のすき間（1px）を空けた外側に置く。開くと、戸は出入口の両脇へ滑り込む。
- かごは戸が全閉になるまで発車せず、着床すると戸を開く。
- 乗場の扉はエンティティとし、開き具合は持たない。かごがその階に着床しているときだけ、かごの戸と同じ開き具合で動く。三方枠など動かない部分は、フェーズ2でブロックにする。
- セーフティシューは、閉動作中の戸板（かご・乗場とも）に生き物（LivingEntity）が触れたら反転する。アイテムなどでは反転しない。
- フェーズ1は中央開き（CO）のみ。2枚片開き（2S）は後で追加する。

## 音声とアナウンス

アナウンスはテンプレートで管理し、再生はクライアントごとに差し替え可能なProviderに任せる。

- **サーバーが送るもの**：アナウンスの種別（「到着」「上へ参ります」など）と階名だけ。
- **同梱音声Provider（標準）**：数字やチャイムなどの音声をOGGで同梱し、つなぎ合わせて再生する。
- **VOICEVOX Provider（後から実装）**
  - ローカルで動いているVOICEVOXエンジンのHTTP API（audio_query → synthesis）でWAVを生成し、キャッシュする。
  - 自由な階名（例：「ブランチマイニング場です」）をその場で読み上げられる。
  - WAVはSoundInstanceで独自のAudioStreamを返し、PCMのまま再生する。
  - エンジンが起動していないクライアントでは、同梱音声に自動でフォールバックする。
- **規約**：VOICEVOXはキャラクターごとに利用規約が異なり、クレジット表記が必要。同梱音声と設定画面にクレジットを表示する。
- メーカーの音声やロゴは使わない。

## 設置方法と動力

設置はウィザード式、方式は機械室レスとし、高速仕様もネザースターを動力にして機械室レスで動かす。

**設置の流れ**

1. 最下階の乗場に制御盤ブロックを置く（実機の機械室レス方式で、三方枠に制御盤が収まっているイメージ）。
2. 階床登録ツールで、各階に立ってクリックし、停止階を登録する。二方向出入口の場合は、各階でどちら側の扉を開くかも登録する。
3. 制御盤のGUIで以下を選ぶ。
   - 機種（P-9／P-11／P-13）
   - 扉の方式（中央開き／2枚片開き）
   - 速度の仕様
   - 階名（アナウンスでも使う）
   - デザイン（プリセット＋部位ごとの変更）
4. 昇降路をホログラムでプレビューし、邪魔なブロックがある箇所を赤く表示する。
5. 確定すると、ガイドレール、各階の乗場ドア、三方枠、乗場ボタン、階床表示器を一括で設置する。

設置後も、制御盤から「リニューアル」としてデザインを変更できるようにする。

**動力**

- **普通仕様**：レッドストーン信号で受電する。信号が切れると「停電」となり、停電時自動着床装置が働いて最寄りの階に着床し、戸を開けて休止する。
- **高速仕様**：制御盤のスロットにネザースターを1個はめると解放される。ビーコンと同じく、ネザースターは消費しない。

## デザインシステム

マイクラのドット調を維持しながら日本式エレベーターを表現し、デザインは「部位 × 素材」のデータ駆動で管理する。

**アートの方針**

- 全部位で1ブロック＝16pxの解像度に統一する。高解像度のテクスチャやなめらかなグラデーションは使わない。
- 寸法は1/16ブロック単位に丸め、ドットの格子を揃える。
- かごの3Dモデルは寸法からプログラムで生成し、素材のテクスチャを敷き詰めて貼る。

**部位**

| 区分 | 部位 |
| --- | --- |
| かご | 側壁・奥壁、袖壁（前壁）、トランサム、ドア、天井と照明、床、幅木、手すり、鏡、防犯窓、展望ガラス |
| 乗場 | ドア、三方枠、幕板（表示器の配置） |

**素材**（MOD側で厳選したリストが基本）

| 用途 | 素材 |
| --- | --- |
| 床 | 石系のみ：磨かれた安山岩・閃緑岩・花崗岩、滑らかな石、深層岩タイル、磨かれたブラックストーン、凝灰岩レンガ。カーペット（16色）を重ねられる |
| 壁・ドア・トランサム・三方枠 | 板材系（オーク、トウヒ、シラカバ、ダークオーク、サクラ、竹など）、カラー（コンクリート、テラコッタ）、ステンレス（ヘアライン、鏡面、エッチング）、クォーツ調 |

- 素材リストはブロックタグ（例：`materials/floor`、`materials/wall`）で定義し、データパックから追加できるようにする。
- バニラのテクスチャはIDで参照するので、リソースパックにも追従する。
- ステンレスなどのオリジナル素材は、バニラの色合いをベースにしたドット絵で描く。
- サーバー側のコンフィグで「自由設定」をオンにすると、任意のブロックを手に持ってGUIにかざして素材にできる。

**個別の機能**

- **トランサム**：素材を壁と同じ／ドアと同じ／別にするかを選べる。かご内の階床表示器を埋め込むこともできる。
- **防犯窓**：なし／縦長スリット／大型の3種類。かごの扉と乗場の扉の窓位置が揃っていると、かごの中が見える。
- **展望仕様**：かごの奥壁または側壁をガラスにし、昇降路の壁（ブロック／ガラス／なし）と組み合わせる。ガラスは専用のレンダリングパスで描く。
- **ボタン**：独自モデルを作る（今は仮の箱）。応答灯の光り方（アンバー、白など）を選べるようにする。

**プリセット**

| プリセット | 壁・ドア | 床 | 特徴 |
| --- | --- | --- | --- |
| マンション標準 | テラコッタ（ベージュ） | 磨かれた安山岩 | 防犯窓あり |
| オフィス | ステンレス（ヘアライン） | 深層岩タイル | トランサムに表示器 |
| 高級 | ダークオーク | 磨かれた花崗岩 | 三方枠はクォーツ |
| 展望 | ステンレス | （未定） | 奥壁ガラス、昇降路の壁もガラス |

## 開発フェーズと未決事項

まず`core`の運転曲線と、2階床・1台のかごの昇降から着手する。

**フェーズ（案）**

1. 2階床・1台：かごの移動、プレイヤーの運搬、当たり判定、扉、ボタン
   - ウィザード設置とボタンができるまでは、デバッグ用コマンドで設置・運転する（`/realelevator spawn <かごを置く階の床面> <機種> <向き> <速度> <ほかの停止階のY…>`（停止階の間隔は4ブロック以上）、`call <階>`（かご呼び）、`hall <階> [up|down]`（乗場呼び）、`open`、`close`、`remove`、`config <panel|car_indicator|left_indicator|hall_indicator> <値>`（配置の設定））。
   - デザインシステムができるまでは、バニラのテクスチャを流用する（壁：鉄ブロック、床：磨かれた安山岩、天井：滑らかな石）。
2. 階床表示、チャイム、同梱音声によるアナウンス、多階床対応、ウィザード設置、高速仕様（ネザースター）、昇降路の機構の描画
3. 車椅子用操作盤、2度押しキャンセル、多光軸ビーム、ナッジング、停電時自動着床
4. デザインシステム（素材、プリセット、防犯窓、トランサム、展望）
5. VOICEVOX連携、複数台の群管理
